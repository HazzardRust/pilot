# The run record lives in the deck store, and the pilot mirrors it into the repository

A pilot that fills its context hands its run to a fresh session after `/clear`, and until now what that session was handed was prose the pilot wrote by hand at the worst moment to be writing it: a hand-off file and an item body indexing it (spec 3 of `docs/design/run-record/architecture.md`). A run's state was scattered across the artefact's status table, the deck's slice table, which hangs off a run row and goes when the session does, and that file. We decided that the run's state is one structured **run record**, keyed by the directory (`repoKey`) and the feature's slug and kept in a `records` list of `deck.json`, and that `deck_status` is its only writer (L5): a call that names a `slug` upserts the record with the whole slice table, whose rows may now carry `branch`, `worktree` and `pr`, and with whichever of `branch`, `artefact`, `findings` (at most 40 lines, each `kept: …` or `dropped: …`) and `next` (one line, at most 400 characters) it sent; a field it leaves out keeps its last value, every cell passes the deck's credential scan, and a call without a slug writes no record, which is what every `deck_status` did before. The tool's answer carries the stored record as a second text block, exactly `JSON.stringify(record, null, 2)` and a newline (L20), and the pilot writes those bytes to `docs/design/<slug>/run.json` in its `feat/<slug>` worktree and commits them at each slice integration and at hand-off (L19). The deck store is canonical and the mirror a snapshot: the store survives `/clear`, restarts and a session's death (ADR 0006), and the mirror survives losing the machine and is readable in the feature PR. The daemon never writes into the repository (ADR 0014), so the pilot writes the mirror. Open thread ids are never stored, because a stored copy goes stale the moment a thread closes (L6): `session-handoff.js` derives them from the open items it already reads, and hands them to the fresh session with the record it fetches from `GET /api/record?repo=`, inside the same fenced, once-only injection as the `handoff` item (L7). Rejected: a separate `deck_record` tool or a `pilot record` CLI (a second thing to forget, and a second surface for one read); the store alone (nothing survives the machine); a git-tracked file alone (a commit in some worktree on every move); a per-run file under `~/.claude/pilot/runs/` (a second writer beside the one atomic store); the pilot writing the mirror from its own input (a snapshot of the request, not of the store); and injecting the record on every SessionStart, which would put it into every non-pilot session in that directory.

**Consequences**: the record outlives every run that writes it, so after `/clear` a fresh session in the same directory is handed it with the `handoff` item and nothing written by hand; the hook reads the open items without naming a `repo` and the record over its own route, so the injection marks none of the user's replies delivered (deck-workspace deferred item 6); a record with no `handoff` item is stored and served but not injected, so a pilot that crashed without handing off is not resumed automatically; the newest record for a directory is the one served, so a second feature in the same directory takes over once it writes one; the record is injected as JSON, so a newline inside a value cannot forge the fence's closing marker; a record at its bounds is clipped at 16,000 characters in the injection; the home screen does not draw the new row fields; and `deck.json` stays `STORE_VERSION 1`, a store written before this reading as holding no records.
