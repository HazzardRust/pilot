# The deck draws a run as a tree computed at render time, behind an edge tab strip later features reuse

The deck showed a run as one flat `Slice | State | Yours` table; the user wanted the run's design on the deck too, as a minimalistic tree with progress visible, and then asked for the table to stay because it is vital information the tree should not replace. We decided the tree is never stored: `deck_status` stays the one flat replace-the-table call the pilot already emits from its artefact's status table, rows keep their two new fields as plain values (`after`, the one other row of the same call this row comes after, and `delivers`, the spec lines it delivers), and `status.mjs`'s `treeOf(slices)` computes the nesting at render time — rejected storing a nested structure on `run.slices`, which breaks every deck already written and makes the pilot nest rows by hand instead of sending a flat table. `after` is resolved and refused inside `newSliceTable`, the one place that already sees the whole call and refuses a duplicate slice name in the deck's own voice: a name matching no other row and a chain that closes a cycle are both refused with a message naming the rows, rather than silently hanging the row from the root and drawing a design that is not the design. Both views live on the page at once, the tree in a tab at the left edge and the table — unchanged — in a tab at the right, with the queue kept in the main column, because the user said the table was vital and the blank space either side of the page's centred 46rem column was the only room already going unused; rejected the tree replacing the table, which was the first draft's default before the user reversed it, and a second page, which is a click away and out of sight. A tab is a native `<details>` element with its `<summary>` styled as the bookmark that peeks out of the edge, the open one given extra room through `details[open] > summary` padding rather than a script; rejected a checkbox-and-label hack, which has no disclosure semantics, and a JS toggle, which the no-JavaScript decision this feature is built under forbids. The strip holds exactly these two tabs today but assumes no fixed count: a later feature that needs its own bookmark adds one to whichever edge fits, without touching how the tree or the table already render.

**Consequences**: the tree is only ever as current as the pilot's last `deck_status` call, since the deck has no repository access of its own to read the artefact directly; every later feature that wants an edge panel inherits the `<details>` bookmark with no JavaScript of its own to write; and `after`/`delivers` are refused by `deck_status` until the slices that add them to the row schema and to `treeOf` land, so this ADR records the shape of the finished feature, not a contract already live on every branch.
