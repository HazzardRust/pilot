# A1 A crew agent's permission prompt is refused by a hook

Feature `yellow-agent` · delivers spec 3 (its last sentence) · source: `../architecture.md` §2 line 3, L17 as amended on itm_9099ba09c0a3 ("A hook refuses it") · after: –

Added after Gate 1, on the user's answer to a blocking question. The F1 probe showed the stall: under a main
session in auto mode, a co-pilot's implementer ran a command matching an `ask` rule, the prompt appeared in the main
terminal and the lane waited on it (PR #348 has the probe and its capture). The install writes eight such rules
(`DEFAULT_BRANCH_ASK`, `scripts/install-settings.mjs`). Facts gathered so far are in `../friction.md`, "Open
findings", the explorer's entry: read it first. They are relayed summaries of Claude Code's docs, not verified:
verify the hook's input and output shape against the current docs once before writing the hook.

## Files owned

- `hooks/permission-refuse.js` (new): the hook.
- `hooks/hooks.json`: one `PermissionRequest` registration, with `id` and `description` as its neighbours have.
- `hooks/test/permission-refuse.test.js` (new): the pins.
- Any test that pins the list of registered hooks or shipped hook files: its count or list only, named in the PR.

## Interface

```
PermissionRequest hook, stdin: the event's JSON
  agent_id present and agent_type starts with "pilot:"  -> deny, with a message; interrupt false
  anything else (the main session, another plugin's agent, unreadable input) -> no output, exit 0: the prompt shows
```

The deny message is the instruction the agent acts on, so it says all of it in one or two sentences: the call was
refused because a crew agent never waits on a permission prompt; record it as a blocked step with its command, do
not retry it and do not route around it, and carry on with the work that does not need it (L17).

## Tests

1. `a crew agent's permission prompt is denied with the blocked-step instruction`.
2. `the main session's prompt is left to the user`: no `agent_id`, no output.
3. `an agent that is not this plugin's is left alone`.
4. `unreadable input leaves the prompt to the user`: no output, exit 0.
5. `the hook never answers allow`: no input makes it print an allow.
6. `hooks.json registers the hook under PermissionRequest`.

## Done

- **Expected**: a crew agent whose call would prompt is told at once that it was refused, and no prompt appears in the main terminal; the user's own prompts are untouched.
- **Verification**: `node --test hooks/test/permission-refuse.test.js`; `npm test`; the F1 probe re-run as the live gate: a scratch repository with a scratch deck (port 4512) and an `ask` rule in that repository's own `.claude/settings.json`, a session started with `claude --plugin-dir <your worktree>` in auto mode, and a crew agent of it running a command the rule matches.
- **Evidence**: tests 1 to 6 failing before and passing after; the probe's capture showing no prompt and the agent's report naming the blocked step, beside F1's capture where the prompt showed.
- **Prohibited**: the hook never answers `allow`, for anyone; no allow or ask rule written into any `settings.json` beyond the scratch repository's own; no edit to `agents/*.md` (the deny message carries the instruction, and the prompt pin has no surplus); never the real `~/.claude/settings.json`.
- **Done when**: the tests and the suite are green and the probe was seen without the prompt. If a plugin cannot register `PermissionRequest`, or the hook does not fire for an `ask`-rule prompt of a subagent, stop and tell `main` with the capture: that goes back to the user.
