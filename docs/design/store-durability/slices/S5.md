# S5 An archived item reads by id and refuses a reply

Feature `store-durability` · delivers spec 8 · source: `../architecture.md` §2, §6 A2, A9 · after: S4 (archivedItem)
Reviewers: `pilot:typescript-reviewer`, `pilot:security-reviewer`
Model: opus — an HTTP route (the security trigger) and A2 is assumed.

## Files owned

- `deck/read.mjs`: `pick` falls back to `archivedItem` for an id the live store lacks.
- `deck/server-routes.mjs`: `/api/items?id=` and the thread page fall back the same way.
- `deck/store-items.mjs`: `threadIn` only; an archived id is refused as archived.
- `deck/test/store-archive-read.test.mjs` (new): the pins.

## Interface

```
S4's archivedItem(id): the fallback all three readers call
threadIn(deck, id): item   // throws DeckRefusal `item <id> is archived (closed <date>); post a new thread`
GET /api/items?id=<archived id> -> 200 { items: [item] }   // read-only
GET /thread/<archived id>       -> 200, the closed thread
```

## Tests

1. `deck_read finds an archived item`: `archivedItem` → `deck_read` with its id returns it whole.
2. `the API finds an archived item`: `GET /api/items?id=` → 200 with the item; an unknown id is still 404.
3. `the thread page renders an archived item`: `GET /thread/<archived id>` → 200.
4. `a reply to an archived item is refused`: `threadIn` → the archived refusal; no file changes.

Rewrite check: replacing the archive's storage keeps every result above while `archivedItem` answers.

## Done

- **Expected**: a user following an old link sees the thread; replying to it says it is archived.
- **Verification**: `node --test deck/test/store-archive-read.test.mjs`; `npm test`; a scratch deck with an archived item opened in the page.
- **Evidence**: tests red before and green after; the archived thread's page seen in a browser.
- **Prohibited**: no write to the archive on read; no change to `store-items.mjs` beyond `threadIn`; no reply moving an item back live.
- **Done when**: the four tests pass, the gate is green and the page has been seen.
