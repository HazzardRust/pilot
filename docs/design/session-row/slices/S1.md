# S1 A session that registers again keeps its run (walking skeleton)

Feature `session-row` · delivers spec 1, 2, 3 · source: `../architecture.md` §2, §5 L1-L2, §6 A1 · after: –
Reviewers: `pilot:typescript-reviewer`, `pilot:security-reviewer`

## Files owned

- `deck/runs.mjs`: `newRun` carries the session key onto the row.
- `deck/store-runs.mjs`: `registerRun` keeps the matching row (pid, repo, key) and refreshes `lastSeenAt`; replaces otherwise.
- `deck/server-routes.mjs`: `POST /api/runs` passes `session` through (:652).
- `deck/client.mjs`: `SESSION_KEY`, sent by `registerSession`; the retry loop untouched.
- `deck/test/register-again.test.mjs` (new): the pins.

## Interface

```
SESSION_KEY: string                                     // deck/client.mjs; minted once per process
registerSession(timeoutMs?): Promise<Run>               // body { repo, pid, session: SESSION_KEY }
POST /api/runs { repo, pid, session? } -> 200 { run, seq }
registerRun({ repo, pid, session? }): Run               // same pid+repo+session: the stored row, lastSeenAt now; else a fresh row
newRun({ repo, pid, session?, now? }): Run              // Run gains session?: string
```

## Tests

1. `a second register with the same key keeps the row and its id`: `registerRun` → one row, the same id, `startedAt` and feature name (set by `setSlices` between the two calls), a later `lastSeenAt`.
2. `a reused pid with a new key is a fresh row`: `registerRun` → a different id, the old table gone.
3. `a register retried over HTTP answers the same run`: `POST /api/runs` → two posts with one key answer 200 with one id; `/api/runs` lists one row.
4. `a session's key is the same at every register`: `registerSession` → two calls post the same `SESSION_KEY`.

Rewrite check: replacing the key with any other per-process identity keeps one row and one id per session and a fresh row per new session.
