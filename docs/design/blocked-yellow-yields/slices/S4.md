# S4 The user's answer resumes a paused ticket at the yellow head

Feature `blocked-yellow-yields` · delivers spec 3 · source: `../architecture.md` §2, A3 · after: S1 (`deck/store-tickets.mjs`)
Reviewers: `pilot:typescript-reviewer`, `pilot:security-reviewer` (the user's reply path moves a ticket)
Model: opus — a state move inside `addReply`'s write, on the user-input path.

## Files owned

- `deck/store-items.mjs`: `addReply` calls `resumeIn` in its own write, for a user reply only.
- `deck/store-tickets.mjs`: `resumeIn`.
- `deck/test/resume.test.mjs` (new): the pins.

## Interface

```
deck/store-tickets.mjs
  resumeIn(deck, question) -> ticket | undefined
    // the question's ticket is paused and no other blocking item naming it lacks a user message:
    // state yellow, delete paused, move the ticket before the repo's first yellow ticket in deck.items
deck/store-items.mjs  addReply(id, said)   // a user reply or Assume the default runs resumeIn in the same write
```

## Tests

1. `the answer resumes at the yellow head`: `resumeIn` → yellow, no `paused`, first of `ticketQueueOf(…, 'yellow')`.
2. `Assume the default resumes too`: `addReply` → the press on the pausing question turns the ticket yellow.
3. `a second unanswered blocking item keeps it paused`: `resumeIn` → undefined; the ticket stays green and paused.
4. `only the user resumes`: `addReply` → a pilot's or the deck's message on the question leaves it paused.

Rewrite check: storing the queue as an ordered id list instead of array order keeps all four results.
