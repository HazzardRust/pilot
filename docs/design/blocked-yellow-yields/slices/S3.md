Feature `blocked-yellow-yields` · delivers spec 2 · source: `../architecture.md` §2, L5, L6 · after: S1 (`deck/lanes.mjs`)

## Files owned

- `deck/lanes.mjs`: `runnableYellowOf` and its use for the yellow `next` and the blocked line.

- `hooks/session-handoff.js`: `CO_PILOT_LINE` admits the blocked shape.
- `deck/test/lanes-runnable.test.mjs` (new), `hooks/test/session-handoff.test.js`: the pins.

## Interface

```
deck/lanes.mjs
  runnableYellowOf(items, repo) -> ticket[]   // open yellow, deck order, none of its own blocking items open
  lanesFrom(items, repo, opts) -> { …, coPilot, yellowClause, refusal, blocked: string | null }
    // next = runnableYellowOf(...)[0]; with yellow tickets and none runnable:
    // coPilot 'co-pilot: empty, blocked: itm_a on itm_q; itm_b on itm_r', blocked = that list, refusal null
hooks/session-handoff.js  CO_PILOT_LINE   // also /^co-pilot: empty, blocked: .../, bounded
```

## Tests

1. `a blocked head is skipped`: `runnableYellowOf` → two yellow, the head with an open blocking question: the second first.
2. `the lane's next is runnable`: `lanesFrom` → `co-pilot: empty → next <second>` and the refusal names the second.
3. `every candidate blocked`: `lanesFrom` → refusal null; `blocked` names each ticket with its question.
4. `the hook keeps the blocked line`: `CO_PILOT_LINE` → matches the blocked shape; a line over its bound is dropped.

Rewrite check: computing the blocked list on the hook side from `/api/record` keeps all four results.
