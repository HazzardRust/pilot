## Behaviours

1. `a pilot walkthrough on a yellow ticket concludes it` (test): `postItem` → ticket state green, `coPilotFor(repo).live` false, `lanesOf(repo).yellowClause` reads `Yellow: empty`.
2. `the answer says so once` (test): `deck_post answer` → one green clause for a walkthrough and for a gate2 that moved the ticket; none for a gate2 on an already-green ticket.
3. `a blocking walkthrough leaves it yellow` (test): `postItem` → state yellow; `deck/test/yield-walkthrough.test.mjs` unedited and green.
4. `another author's walkthrough moves nothing` (test): `postItem` → an architect-stamped walkthrough is stored and the ticket stays yellow.
5. `the incident replays green` (test): `postItem` → `itm_ab39b4603222`'s fields (author pilot, non-blocking, 1-slice yellow ticket) read green after 1 call.

Seam changes as built (pilot, from the S1 report):

- `concludeOn` returns nothing; `deck_post` reads the ticket's state before and after the post for the clause.
- `concludeOn` lives in `deck/store-stage.mjs`, keeping `store-items.mjs` under the 800-line cap of `facades.test.mjs`.
- A gate2 on a green ticket that is not live is accepted when a concluding walkthrough of that ticket exists, named or not (`ticketNamedBy`).
- `deck/test/ticket-need.test.mjs`, `co-pilot.test.mjs`, `ticket-tool-yellow.test.mjs` store their walkthrough fixture with `postStored`; `posting a walkthrough leaves its ticket yellow` is deleted, the rule it pinned being the one this slice replaces (assumed).
- Behaviour 4 is a guard: green before the change too. Behaviour 2 is three tests.

Rewrite check: storing the move in a separate write after the post keeps 1-5 only if both land before the call returns.
Misses: whether QA and the pilot read the new clause; the QA walkthrough on a scratch deck reads it.
