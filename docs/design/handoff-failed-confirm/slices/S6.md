## Files owned

`render.mjs` below means its `render-*.mjs` sibling holding the named code, with anchors from before the split: see `../brief.md`, "render.mjs after the split".

- `deck/ui/js/live.mjs`: `apply` (`:141-248`) swaps only the shown page's regions, by name, so it cannot carry the overview (`queue`) to a thread page (`kind`, `nav`, `position`, `thread`, `reply`). It gains the page-kind swap: when the fetched page's set of `data-live` names differs from the shown one's, `<header>`, `<main>` and `document.title` are replaced whole, and the panels and `.strip.right` go through the per-region path as today.
- `deck/ui/js/inplace.mjs` (S4's): `install(env, refresh)`. A `data-in-place="move"` form is fetched following redirects; the address it landed on is pushed (`history.pushState`) and `refresh` runs, as `navigate.mjs:44-46` does. The submitter is blurred first, or `busy` skips the region holding it (`navigate.mjs:40-44`).
- `deck/ui/js/deck.mjs`: hands `live.mjs`'s `refresh` to `inplace.mjs`'s `install`.
- `deck/ui/render.mjs`: `data-in-place="move"` on Add deck (`:1156`), Create (`:1222`), Remove (`:1257`) and Make tickets (`:1537`).
- `deck/test/live.test.mjs`: the page-kind swap pin.
- `deck/test/inplace.test.mjs`: the move pins.
- `deck/test/{create,make-tickets,add-deck,remove-deck}.test.mjs`: each form carries `data-in-place="move"`.

## Interface

```
install(env, refresh): void            // inplace.mjs, S4's seam; `refresh` is live.mjs's
<form method="post" action="/route" data-in-place="move">   // fetched, then the address moves to where it landed
refresh(): void                        // live.mjs; now also crosses page kinds
S4's data-in-place: unchanged for every other form
```

- The server is unchanged: the 303s at `server.mjs:1258`, `:1276`, `:1299`, `:1304` are followed, and the fetch's final URL is the address pushed.
- A 4xx or a dropped request posts the form for real (S4's rule), so `/remove-deck`'s 400 on a live session still reads.
- Create's confirm step stays as A1 says: its Next is a submit `confirm.mjs` prevents and the typed name rides in the form, so only the final Create is fetched.

## Tests

1. `refresh carries the overview to a thread page`: `refresh` → after a `pushState` to a thread's address, the page holds `thread` and `reply` and no `queue`, with no navigation.
2. `Create moves to the new thread in place`: `data-in-place="move"` → one fetch, `pushState` to `/thread/<id>`, then `refresh`.
3. `Create's Next is not fetched`: `data-in-place="move"` → the first submit is prevented and nothing is fetched.
4. `a refused Add deck draws its reason in place`: `data-in-place="move"` → `pushState` to `?refused=`, and the refusal is drawn beside the + box.
5. `Remove lands on the overview in place`: `data-in-place="move"` → `pushState` to `/`; a 400 posts for real.

Rewrite check: replacing the page-kind swap with a full-body swap keeps tests 1-5.

## As built (co-pilot, 2026-10-10)

The page-kind swap runs when `body[data-item]` or the region names inside `<main>` differ, not on any `data-live` name: a
thread's `position` region comes and goes with its list, and counting it would wipe a typed reply. A fetched page with no
`<main>` (a refusal or an error page) moves nothing. `usage.mjs` and `escape.mjs` look their elements up on use, and Create's
Next listener in `confirm.mjs` is capturing. The account's usage readings carry across a swap; `ctx` does not. Known gap:
Esc on a thread reached in place navigates to `/` (`document.referrer` is stale).
