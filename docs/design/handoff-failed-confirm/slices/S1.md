## Interface

```
<[data-confirm-row]>                       // the confirm row: a Tickets li, a choice row
  <button type="submit" data-confirm ...>  // trigger: its own name/value/form as today
  <div class="step sure" hidden><p>{sentence}</p>
    <button type="submit" name={trigger.name} value={trigger.value} form={trigger.form}>Confirm</button></div>
install(env): void                         // confirm.mjs, unchanged signature
SPECS[KIND_HANDOFF].ask: "Treat the session this went to as lost, and brief a fresh one from this hand-off?"
SPECS[KIND_CREW_HANDOFF].ask: "Treat this agent as lost, and brief a fresh one from its branch?"
askFor(kind: string): string | null
```

The row's `data-confirming` attribute is set while the confirm shows. Revert happens on any click but Confirm, and on Escape. Exactly one row is confirming at a time.

## Tests

1. `a handoff row confirms in place, card and page, both kinds`: `askFor` → the row carries the trigger, and a hidden `.sure` holds the kind's sentence and a Confirm with `choice=Handoff failed`.
2. `the first press on a trigger is prevented and nothing is fetched`: `data-confirm` → in a sandbox of confirm.mjs and reply.mjs together, no fetch.
3. `Confirm submits the trigger's value through the reply fetch`: `data-confirm` → one call, with `choice=Handoff failed`.
4. `a click elsewhere or Escape reverts and posts nothing`: `install` → the row is back and nothing is fetched.
5. `Continue still blanks its row and reverts`: `install` → the moved `confirm.test.mjs` pins pass.
6. `a handoff with no options draws no trigger, and an audit's row answers in one press`: `data-confirm` → on neither row.

Rewrite check: replacing confirm.mjs's implementation behind `data-confirm` keeps all six results.
