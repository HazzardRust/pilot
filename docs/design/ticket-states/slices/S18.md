# S18 Blocking questions: only a blocking question stops its own ticket turning red

Feature `ticket-states` · run 2 · delivers spec 17 (revised) and keeps spec 16's evidence · source: `../architecture.md` §2, L22 (revised, itm_4c0faaf3ea87) · after: S16 · added on the user's word, 2026-10-02 ("s18"); the second added slice of the run

## Why

S16's autonomous walk showed L22 as first worded let a parked ticket's open question refuse the *next* ticket's `gate2` post, so a second autonomous run never reached red. The user rejected both patches and redesigned the gate: the only question that stops a ticket turning red is a **blocking** one, on that ticket; everything else is assumed mid-run and revised at the end.

## Definition (the user's, on the deck)

A question is **blocking** when both hold: (a) its answer is unreasonably expensive to revise after the fact — a schema or migration, an auth or trust boundary, a public API shape, irreversible data; a slice re-cut is *not* on the list; and (b) no safe assumption exists. The pilot marks it `blocking: true` and the body says why on both counts. Every other question is **plain**: the pilot takes its recommended default, records it as assumed, carries on, and the question waits on the ticket as red-phase grilling.

## Rules

1. A `question` names its ticket (S14). `deck_post` gains `blocking` (boolean, question only, default false).
2. A `gate2` **post** is refused only by an open *blocking* question on *its own* ticket, by name. Questions on other tickets never refuse anything. A question naming no ticket refuses nothing (it is a chat-level question; the pilot's prose stops posting them).
3. A `gate2` **Sign off** is refused by any open question on its ticket (S14, unchanged).
4. `gate1` keeps ADR 0029's rule: refused by any open question on its ticket.
5. The deck's away answer ("the user is away: go with <recommended>") applies to plain questions only; a blocking question is never auto-answered.
6. A blocking question stops nothing until the gate: the pilot carries on with every slice and every part of the ticket that does not stand on the answer. Only when nothing independent is left does the run park the ticket with `finished: "blocked"` (S13); `nextTicketOf` skips a yellow ticket that has an open blocking question until it is answered, in both modes, then the chain takes it up from the record. Attended order (spec 18) still puts a ticket with open questions first — plain or blocking.
7. A blocking question offers **Assume the default** as a one-click option; pressing it answers with the recommended option and makes the question plain (the refusal lifts). The reply is recorded as the user's.
8. The Stop gate (`hooks/stop-gate.js`, `hooks/lib/deck.js`) is unchanged: an open question on the live ticket holds the turn; a parked ticket's does not. The pilot's prose parks `blocked` before ending a turn with an open blocking question in autonomous mode.
9. The Tickets tab's red row and the question's card show a `blocking` badge; the row's count reads `N questions (M blocking)`.

## Interface

```
deck_post { kind: 'question', ticket, blocking?: boolean, ... }
isBlocking(item): boolean            // kind question, open, blocking === true
openBlockingOf(items, ticketId)        // what refuses a gate2 post
reply 'Assume the default'           // on a blocking question: answers with recommended, sets blocking false
nextTicketOf(items, repo, mode)        // skips a yellow ticket with openBlockingOf non-empty
```
