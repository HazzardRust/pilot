# S2 The pilot's hooks ignore threads it does not own

Feature `thread-ownership` · delivers spec 2 (the hooks) · source: `../architecture.md` §3 "The pilot-only hooks", A8 · after: S1

## Files owned

- `hooks/lib/deck.js`: `ownerOf(item)`, the hooks' spelling of S1's `ownerOf`.
- `hooks/stop-gate.js`: `answered` counts only threads whose owner is `pilot`. It does not compute the grace period (L4): it cannot see `lastActive`, which lives in the daemon's memory. An overdue reply reaches the pilot through its parked wait and the inbox hook (S5 pins the inbox hook's call). Once S5's `fallBack` makes the thread the pilot's, this hook blocks on it like any other.
- `hooks/inbox-alert.js`: only a comment naming A8. Its authorless `deck_wait` is already the pilot's under S1's `waiterKind`, and a test pins that.
- `hooks/test/owner-hooks.test.js` (new): the pins.
- `hooks/test/join.test.js`: `ownerOf` agrees with `deck/items.mjs`'s on the same items.

## Interface

```
ownerOf(item): 'pilot' | 'qa'     // hooks/lib/deck.js; same rule as S1's ownerOf, pinned equal by join.test.js
S1's waiterKind: why inbox-alert's authorless wait is the pilot's
```

## Tests

1. `the stop gate does not block on an answered thread qa owns`: a QA-owned item with a user reply last produces no block.
2. `the stop gate still blocks on an answered thread the pilot owns`.
3. `the inbox hook injects nothing for a reply on a qa thread`: against a live test deck, a QA-owned reply yields no notice and the cursor moves past it.
4. `the inbox hook still injects a reply on a pilot thread`.
5. `hooks ownerOf agrees with the deck's` (join test): same answers over old, QA, chat and created items.
