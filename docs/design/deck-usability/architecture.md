# Deck — answering a run without the deck getting in the way

## 1. Problem

The deck is the only place the user answers a piloted run, and using it for real
is slower and messier than it should be. Refreshes interrupt typing. A long
thread buries the next one. They cannot tell at a glance whether a reply they
gave has been seen or acted on. Walkthroughs are verbose and ask them to verify
things the agent could verify itself. Stale runs linger in the status section.
There is no way to answer from the home page. And the MCP bridge reports
"Connection closed" at the start of a session while the daemon is alive.

## 4. Ubiquitous language

| Term | Means exactly |
| --- | --- |
| **Live region** | An element marked `data-live` whose inner HTML the deck replaces when something changes. Everything outside one belongs to the user: the reply box, the caret, the scroll, the open panels, the selected tab. |
| **Card** | One item as a list shows it: status bar, title, preview, quick answers. Never the whole body. The **thread page** is where the whole body lives. |
| **Thread state** | The five derived states of line 4: `posted`, `not picked up yet`, `the pilot has it`, `the pilot replied`, `resolved`. Derived, never typed. |
| **Hand-off** | The moment `deck_wait` or `deck_read` gives a user's reply to a session. Recorded as `deliveredAt` on that reply. Not "the pilot agreed", not "the pilot acted". |
| **Step** | One line of a walkthrough, `do this → correct result`. The arrow is the only structure. |
| **Browser count** | How many pages are on `/events` right now, counted apart from parked `deck_wait` calls. |
| **Stale run** | A run with no activity for 48 h, or one the user dismissed. Distinct from an **ended run**, whose session's pid is gone. |
| **Teaching** | One pilot-side message in a decision thread, written by the **teacher** (`pilot-teacher`) after the user pressed "Teach me": what is being decided, the alternatives, why the default, what it costs, what would change the answer. Never a resolution, never a question back. |
| **Grilling depth** | The user's answer, once per run, to how many decisions reach them: *every* locked decision, or *forks* only — the ones whose paths produce materially different deliverables. |
