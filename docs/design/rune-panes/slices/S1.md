## Interface

```
pub const CENTRE: &str = "centre-scroll";      // the viewport's key prefix; + screen and thread id
pub fn center(s: &State, cx: &mut Cx<State>) -> El   // header fixed, the rest in the viewport
pub fn key(s: &mut State, ev: &rune::KeyEvent, tx: &mut Tx) -> bool
// PageUp/PageDown: Tx::scroll_page(±1); Home/End: scroll_to_y(0) / scroll_to_bottom; Up/Down: 40 px
// never when a text field holds the key; Alt+arrows, Left and Escape keep their meaning
```

## Behaviours

1. `a thread opens at its last message` (test): `center` → a seeded 60-message thread in a 900 px window draws its last message inside the window on the first settled frame.
2. `the wheel reaches the top and the bottom` (test): `center` → `Runtime::wheel` up puts the title inside the window, down puts the last message back.
3. `keys scroll the centre` (test): `key` → PageUp moves the last message out; End brings it back; Home shows the title.
4. `a key in the reply box is not a scroll` (test): `key` → with the reply box focused, End moves 0 px.
5. `home and the items page open at the top` (test): `center` → a seeded queue of 40 cards: the first card in the window, the wheel reaches the last.
6. `a live refetch keeps a scrolled-up thread in place` (test): `center` → scrolled up, a new view of the same thread with one more message leaves the first visible message's y within 1 px.
7. `the scroll bar drags` (look): the user drags Rune's overlay bar to the bottom of a long thread in the built window.

Rewrite check: replacing the one viewport with any other scroll container keeps behaviours 1-6.
Misses: how the scroll feels on a trackpad and the bar's look; the user reads both on the walkthrough.
