# S6 A bounded glossary log that travels with the glossary

Feature `project-glossary` · delivers spec 10, 11 · source: `../architecture.md` §2, §5 L12, §6 A4 · after: S1 (`parseGlossary`)
Reviewers: `pilot:typescript-reviewer`, `pilot:security-reviewer`
Model: opus — a CLI writing a tracked file from arguments (security trigger), and a new file format.

## Files owned

- `GLOSSARY-LOG.md` (new): a title, one line saying what it is and its 200-row cap, the table; seeded with this run's rows: **Glossary**, **Stale term**, **Glossary log** added, and S1's 7 reworded entries changed, run `project-glossary`.
- `scripts/glossary-log.mjs` (new): the row shape, the cap, the agreement check, and the CLI.
- `scripts/test/glossary-log.test.mjs` (new): the pins, and `checkLog` over the repository's two files.

## Interface

```
type LogRow = { date: string /* YYYY-MM-DD */, run: string /* slug, words */, change: 'added' | 'changed' | 'removed', term: string }
readLog(text: string): LogRow[]                                  // table rows, oldest first; a malformed row throws naming its line
appendLog(text: string, row: LogRow, cap = 200): string          // the new file text, oldest rows dropped past cap
checkLog(logText: string, glossaryText: string): { line: number, problem: string }[]
  // over cap; newest row `removed` but the term is in the glossary; newest `added`/`changed` but absent; a row without a run
queryLog(rows: LogRow[], opts?: { term?: string, limit?: number }): LogRow[]   // newest first, limit default 20
node scripts/glossary-log.mjs check [--log GLOSSARY-LOG.md] [--glossary GLOSSARY.md]   // exit 0, or 1 with one line per problem
node scripts/glossary-log.mjs append <change> <term> --run <slug> [--date YYYY-MM-DD]   // writes GLOSSARY-LOG.md
node scripts/glossary-log.mjs show [--term <t>] [--limit <n>]                           // rows as a table
S1's parseGlossary
```

## Behaviours

1. `three appends are three rows naming their run` (test): `appendLog` → add, change, remove of one term give 3 rows in order, each with its run slug, no sha.
2. `the log is capped` (test): `appendLog` → 201 appends leave 200 rows, the first one gone.
3. `a disagreement fails the check` (test): `checkLog` → a term whose newest row is `added` but not in the glossary gives 1 problem naming it; one whose newest row is `removed` but present gives 1.
4. `a term with no row passes` (test): `checkLog` → a glossary term with no row (dropped by the cap) gives 0 problems.
5. `read in part` (test): `queryLog` → `term: 'Glossary'` returns only its rows; no options returns at most 20.
6. `the repository's log agrees` (test): `checkLog` → on `GLOSSARY-LOG.md` and `GLOSSARY.md`, 0 problems.
7. `the log reads without git` (run): both files copied to a scratch directory with no `.git`, `show --term Glossary` there prints the same row.

Rewrite check: any store of these rows giving these results keeps 1-6.
Misses: a run that edits the glossary and appends no row; S7's `unlogged` candidate reads it.

## Done

- **Expected**: a user copies `GLOSSARY.md` and `GLOSSARY-LOG.md` to another project and can still see which run added or changed each recent term.
- **Verification**: `node --test scripts/test/glossary-log.test.mjs`; `node scripts/glossary-log.mjs check`; `npm test`.
- **Evidence**: behaviours 1-6 red before, green after; behaviour 7's output pasted in the report.
- **Prohibited**: no git call in `glossary-log.mjs`; no `shell: true`; no write outside the `--log` path; no edit to `scripts/glossary.mjs` or `GLOSSARY.md`.
- **Done when**: the 7 behaviours hold and `npm test` is green.
