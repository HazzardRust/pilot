# S8 Merge first names an earlier feature this head shares unmerged commits with

Feature `red-lands-on-pilot` · delivers spec 4 (revised on itm_f05ad052b4ec) · source: `../architecture.md` §2 spec 4, §5 L7 · after: S3 (`scripts/land.mjs` `mergeFirst`) · added slice, from QA's finding on walkthrough itm_525b9cfdd503
Reviewers: `pilot:typescript-reviewer`, `pilot:security-reviewer`

## The gap

S3 keeps a PR in `merge first` only when its head is an ancestor of this landing's feature tip. A lands on pilot; B is integrated on top of it (B carries A's commits); A gets a Gate 2 fix and re-lands, so A's head moves; B then lands and its `merge first` reads `none`, because A's new head is no longer an ancestor of B. Merging B's PR first would ship A's pre-fix code to main with no warning.

## The rule

An open feature PR (base the default branch, head `feat/*`, not this head) is merge-first when both hold:

1. it **shares a commit with this head that is not on the default branch**: `git merge-base <pr.headRefOid> <source>` exists and is not an ancestor of `refs/remotes/origin/<default>`;
2. its **first landing on pilot came before this one's**: on `origin/pilot`'s first-parent history, the oldest `Merge feat/<its slug> into pilot` commit (S5's message) is older than the oldest `Merge <head> into pilot`; a PR with no landing on pilot is not merge-first (it stands on nothing landed, and this head cannot carry it).

Refined at implementation (co-pilot, assumed; spec 4 unchanged): in rule 1 a shared base counts only when it is also not an ancestor of the first parent of that PR's first landing on pilot, so the shared commit reached pilot with that PR's own code. Without it a feature cut from `origin/pilot` (S3 test 1's `stray`) shares the earlier landings and reads as merge first. `git merge-base --all` is used, any base qualifying; a merge-base git cannot answer throws. Known limit: an earlier feature rebased or force-pushed after landing shares only what pilot held before its landing and escapes the rule.

Ordering stays oldest landing first; drafts stay marked `(Gate 2 open)`; the PR comment of S3 is unchanged.

## Files owned

- `scripts/land.mjs`: `mergeFirst` only; the two filters above replace the ancestor filter; one helper reading the first-parent log of `origin/pilot` once (`git log --first-parent --format=%H%x09%s refs/remotes/origin/pilot`), not one `git` call per PR per commit.
- `scripts/test/land.test.mjs`: the pins below on its scratch bare origin with `gh` injected; S3's tests 1–4 keep passing.

## Tests

1. `a re-landed earlier feature is still merge first`: A lands, B cut on A is landed, A gets a fix commit and re-lands → B's line reads `merge first: #A (Gate 2 open)` (A's head is no longer an ancestor of B).
2. `an unrelated feature is not merge first`: A and C share no commit off main → C's line reads `merge first: none` with A on pilot.
3. `a later feature is not merge first`: as S3's test 1, B landed after A → A's line reads `none`.
4. `a feature never landed is not merge first`: D cut on A's commits but never landed → A's line does not name D.

Rewrite check: swapping the first-parent log for a `git for-each-ref`-based lookup keeps all four results.
