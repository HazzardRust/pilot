# S8 The pilot's Resolving and Land again replies

Feature `gate2-frees-lane` · delivers spec 5 · source: `../architecture.md` §2, L5, L7 · after: S7 (`landing.conflict`, `deck/store-items.mjs`), S2 (`deck/server-tools.mjs`)
Reviewers: `pilot:typescript-reviewer`, `pilot:security-reviewer`
Model: opus — a reply re-runs a process that pushes to pilot without a new press, a trust boundary.

## Files owned

- `deck/store-items.mjs`: the pilot's `Resolving` and `Land again` replies on a gate2 with a `conflict`; any other author refused.
- `deck/server-tools.mjs`: `deck_reply`'s `Land again` starts the landing once the store has taken it.
- `deck/test/land-again.test.mjs` (new): the pins.

## Interface

```
deck/store-items.mjs
  addPilotMessage(id, text)
    // on a gate2: 'Resolving …' stores landing.conflict.resolving = at (stops armConflicts)
    //             'Land again'  clears conflict, landing → running; refused unless refused + conflict, and from the pilot
deck/server-tools.mjs
  deck_reply { id, text: 'Land again' } -> startLanding(id)   // S5's fixed argv, nothing from the reply
```

## Tests

1. `Resolving stops the clock`: `addPilotMessage` → `conflict.resolving` set; `armConflicts` then posts nothing.
2. `Land again re-runs the landing`: `deck_reply` → one spawn of `[PILOT_BIN, 'land']` in the record's worktree, and the gate2 reads `running`.
3. `Land again without a conflict is refused`: `addPilotMessage` → refused on a landed, a running and a non-conflict refused gate2.
4. `Land again from anyone but the pilot is refused`: `addPilotMessage` → refused for a QA or architect author, and the user's text is a plain reply.

Rewrite check: a `deck_ticket` action instead of a reply keeps results 2 to 4.
