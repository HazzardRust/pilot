# S5 The rules ledger counts the commits a merge is bringing in

Feature `architect-runs-red` · delivers spec 8 (added) · source: `../architecture.md` §2 · after: –
Reviewers: `pilot:typescript-reviewer`
Model: sonnet — one git argument and one test, every change specified.

Added by the co-pilot at integration (found issue, build-now rule). `pilot integrate` gates a slice inside
`git merge --no-commit`. `scripts/build-rules-ledger.mjs:70` walks `git log ... HEAD -- rules/`, so a slice
with more than one commit touching `rules/` has versions reachable only from `MERGE_HEAD`. `--check` then
calls the ledger stale and the integration goes red, although the same tree passes once the merge is
committed. S4's integration failed this way at 2da36cbb + b4494072: `orchestration.md` f9def0b9, from
56191b87 and a9641329, was dropped.

## Files owned

- `scripts/build-rules-ledger.mjs`: the history walk also takes `MERGE_HEAD` when it exists.
- `scripts/test/rules-ledger.test.mjs`: the pin.

## Interface

```
git log --full-history --format=%H HEAD [MERGE_HEAD] -- rules/   // MERGE_HEAD only when `git rev-parse -q --verify MERGE_HEAD` succeeds
```

## Tests

1. `a merge in progress counts the incoming commits`: `git log --full-history --format=%H HEAD [MERGE_HEAD] -- rules/` → in a temp repo where a branch edits `rules/x.md` twice, merged
   `--no-commit` into main, `--check` passes on the ledger built from the tree as it stands, and that ledger holds
   the intermediate version's hash. It fails before the change.

Rewrite check: rewording the walk keeps `MERGE_HEAD` named only when it exists, and `--check` unchanged outside a merge.
