# S8 GitLab answers the same checks

Feature `ci-gate` · delivers spec 8 · source: `../architecture.md` §2, §3 Seams, §5 L1, L3 · after: S1 (the **Host** `checks` verb)
Reviewers: `pilot:typescript-reviewer`, `pilot:security-reviewer`
Model: opus — it widens the `glab api` allowlist, a process-start trust boundary.

## Files owned

- `deck/host-gitlab.mjs`: `checks(sha)` over `glab api projects/:id/repository/commits/<sha>/statuses`; allowlist GET of that path only.
- `deck/test/host-gitlab-checks.test.mjs` (new): contract over a fake `glab` run, 0 spawns.

## Interface

```
S1's Host.checks(sha) -> Check[]
  // GitLab statuses (latest retry only): success -> pass; failed, canceled -> fail;
  // created, pending, running, manual, waiting_for_resource, preparing, scheduled -> pending; skipped -> pass
```

## Behaviours

1. `statuses map to outcomes` (test): `Host.checks` → failed, running, success give fail, pending, pass, names kept.
2. `the verdict is the same` (test): `Host.checks` → through S1's `checksAt`, a failed job reads red with its name.
3. `only the one GET reaches glab` (test): `Host.checks` → a short sha, `--method POST`, or another path throws `not a host verb`, no run.

Rewrite check: reading `pipelines?sha=` instead keeps 2 if a failed pipeline still names its jobs.
Misses: a real GitLab project; no GitLab remote exists here, so QA reads the contract test only.
