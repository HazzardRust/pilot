# S4 a release run publishes three binaries and pins them

Feature `prebuilt-rune` · delivers spec 1, 2, 9 · source: `../architecture.md` §2, §5 L1, L5-L7, §6 A1, A7-A9 · after: S1 (`release.json` format, `readPin`)
Reviewers: `pilot:typescript-reviewer`, `pilot:security-reviewer`
Model: opus — a workflow holding `contents: write` that publishes executables, the security trigger.

## Files owned

- `.github/workflows/rune-release.yml` (new): build matrix and pin on every trigger; draft, upload, publish only on a scratch tag (A9) or a dispatch; pin commit only on a dispatch.
- `scripts/rune-pin.mjs` (new): `pinRelease`, run by the publish job over the downloaded artifacts.
- `scripts/test/rune-pin.test.mjs` (new): the pins, on fixture files with each OS's header.
- `docs/OPERATING.md`: the release step, one paragraph: bump, dispatch, merge.

## Interface

```
on: pull_request paths [.github/workflows/rune-release.yml, scripts/rune-pin.mjs, deck/rune/Cargo.toml, deck/rune/Cargo.lock]
      (build + pin only: 3 binaries and release.json as artifacts, release.json in the job summary; no release, no write)
    push: tags ['rune-scratch-*'] (A9: the same, plus a prerelease on that tag; no commit)
    workflow_dispatch (version from .claude-plugin/plugin.json, tag v<version>, release, pin commit to the dispatched ref)
jobs: build (windows-latest x64, macos-latest arm64, ubuntu-22.04 x64 + libxkbcommon-dev libwayland-dev;
             cargo build --release --locked --manifest-path deck/rune/Cargo.toml) -> pin (contents: read) -> publish (contents: write; tag and dispatch only)
assets: pilot-deck-win32-x64.exe, pilot-deck-darwin-arm64, pilot-deck-linux-x64
pinRelease({ version, tag, dir }): { json: string, problems: string[] }   // json is S1's release.json shape
```

## Behaviours

1. `a pin round-trips through the reader` (test): `pinRelease` → its `json` written to a temp root gives each target's sha256 through S1's `readPin`.
2. `a wrong header is a problem` (test): `pinRelease` → a Linux ELF under the Windows name, or a missing target, lands in `problems` and the job fails.
3. `a build run yields three binaries` (run): the feature PR's run lists exactly 3 binary artifacts; under A9 also `git push origin rune-scratch-<sha7>`, then `gh release view rune-scratch-<sha7> --json assets` lists the same 3.
4. `the pins match independent hashes` (read): each binary downloaded (artifact or asset) and hashed with `certutil`/`shasum -a 256` equals the summary's `release.json`, 3 of 3.

Rewrite check: any workflow keeps `release.json` naming exactly the 3 targets with hashes of the published bytes.
Misses: the dispatch path's pin commit, which needs the file on main; the first real release after landing reads it.

## Done

- **Expected**: a PR run gives 3 verified binaries and a `release.json` that S1's reader accepts; under A9 a scratch tag also publishes them.
- **Verification**: `node --test scripts/test/rune-pin.test.mjs`; `npm run test:changed -- --since=<base sha>`; the PR run's log and artifacts; under A9 `gh release view`.
- **Evidence**: the green run URL, the 3 binaries, 3 matching hashes; under A9 the scratch release and tag deleted after QA has used them.
- **Prohibited**: no third-party action; no secret beyond `GITHUB_TOKEN`; no `contents: write` on the build jobs; no upload after publish.
- **Done when**: the tests pass, the PR run is green with 3 binaries (and the scratch release under A9), and the hashes match.
