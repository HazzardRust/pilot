# S23 A thread move fetches its view at once (added)

Feature `rune-deck-ui` · delivers spec 14 (added) · source: `../architecture.md` §2, S9's fix-round report · after: S9 (`reply` region `id`)
Reviewers: `pilot:rust-reviewer`
Model: sonnet — the fetch path exists in `live.rs` (`follow`); only when it runs changes, plus one guard in `app::poll`.

Added by the co-pilot (2026-11-20) from S9's security re-read: the thread arrows (`regions/thread.rs` `go`) move
`State.query`, but `live.rs:40` `ask` only stores it and `follow` refetches only on connect or a deck `changed`
event, so the thread region keeps drawing the thread just left until the deck next changes, and a late view of
that thread can redraw its reply box after S9's reset (a draft typed there carries into the next box). On the
page a move draws the new thread at once.

## Files owned

- `deck/rune/src/live.rs`: `ask` wakes the reader so the new query is fetched now, not on the next change.
- `deck/rune/src/app.rs`: in `poll`, a fetched view whose thread id is not `State.query`'s is dropped (the reply region's `id` from S9).
- `deck/rune/tests/thread.rs`: the pins.

## Behaviours

1. `a move shows the next thread without a deck change` (test): scratch deck with two threads, open the first, press ›, no write to the deck → within the poll timeout the drawn thread is the second.
2. `a late view of the thread left draws nothing` (test): a view for the first thread arriving after the move to the second → no reply box drawn, the draft stays empty.
