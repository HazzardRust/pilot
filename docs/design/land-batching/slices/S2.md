# S2 A landing reads every tip from one snapshot

Feature `land-batching` · delivers spec 4 · source: `../architecture.md` §3, §5 L4 · after: S1 (`scripts/land.mjs`, `gitView`)
Reviewers: `pilot:typescript-reviewer`
Model: opus — choosing which tip reads are one epoch needs reading each call's write order in `land.mjs`.

## Files owned

- `scripts/git-view.mjs`: `tipOf` and `holdsIn`.
- `scripts/land.mjs`: `catchUp`, `landCaughtUp` read HEAD, pilot and `origin/<head>` through `tipOf`.
- `scripts/test/git-view-tips.test.mjs` (new): the snapshot's answers and its epoch.
- `scripts/test/land-pin.test.mjs`: the count bar moves to ≤ 32.

## Interface

```
tipOf(git: Git, ref: string): string | null   // full ref or HEAD; one for-each-ref snapshot per epoch, HEAD by one rev-parse
holdsIn(git: Git, args: string[]): boolean    // exit status 0, remembered per epoch like a read
S1's gitView: the view both read through
S1's countGit: the landing's git count
```

## Behaviours

1. `every tip in an epoch costs one spawn` (test): `tipOf` → `refs/remotes/origin/pilot`, `refs/remotes/origin/feat/x` and a missing ref in one epoch spawn 1 git and answer the two SHAs and null.
2. `a write refreshes the snapshot` (test): `tipOf` → after a `commit` through the view the moved branch reads its new SHA.
3. `an ancestry check is asked once` (test): `holdsIn` → the same `merge-base --is-ancestor` twice in one epoch spawns 1 git.
4. `one landing spawns at most 32 git` (test): `countGit` → S1's landing pin spawns ≤ 32 and still prints the pinned lines.

Rewrite check: answering tips by `rev-parse` per ref instead keeps 1-3's answers; only the counts move.
Misses: a ref name with a space or a symref target; the security reviewer reads `tipOf`'s ref handling.
